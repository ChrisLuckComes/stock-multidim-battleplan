# 报告生成：battle_analyze.py + report_render.py（模板化出报告）

> 2026-09-21 建。**动因是实测出来的，不是"感觉慢"**：
> 东材 601208 那一轮从用户发消息到报告定稿共 **652.8s ≈ 10.9 分钟**（22 轮模型往返）。
> 拆开看，**写报告那一段占 97.9s，其中 92.1s 是模型逐字输出 HTML**；
> 而 43,049 字节 / ≈12,783 token 的报告里，
> **CSS 骨架 6.3% + 表格 40.7% + 卡片外壳大半 ≈ 65~70% 是"每次形态一样、只有数字不同"**。
> 模型吞吐实测 ≈139 tok/s ⇒ 这部分每轮都在白烧 60~70 秒。
> 于是把骨架固化成模板，模型只写判断。

## 1. 两步流程（替代"手写 43KB HTML"）

```bash
cd <skill 目录>

# ① 出数据（一次取数，rule123 + probe 共用同一份快照；量价/赔率/同行/分时全部算完）
python battle_analyze.py 601208 --account 50000 --cash 28426 \
    --peers 600183,688519,603186,605589,002636 \
    --peer-names "600183=生益科技,688519=南亚新材,603186=华正新材,605589=圣泉集团,002636=金安国纪" \
    --out out_cn/analysis_601208.json
#    → stdout 打印紧凑人类摘要（模式/买区/止损/目标/分位/全档赔率 Top10/分时/同行）

# ② 出报告（模板 + 数据 + notes）
python report_render.py --data out_cn/analysis_601208.json \
    --notes notes.json --out "C:/Users/luoyunlai/stock-reports/601208-20260921.html"
#    → 自动做标签配对自检，异常时 rc=1
```

> **`--name` / `--theme` 也要传**（2026-09-23 补）：不传时 `meta.name` 会退化成代码本身
> （页头、首屏 KPI、「主线概念」栏全是裸代码，扫雷段与龙头对照段也没法写板块）。
> 中文值一律走**参数列表**（写个 `.py` 包装脚本用 `subprocess.run([...])` 调），
> PowerShell / Git Bash 直接传中文都可能被 GBK 吃掉（见 pool-sync skill §0.3）。
>
> **`--cash` 是必须传的**：`--account` 是账户总额（用于风险预算 = ¥50,000 × 1.5%），
> `--cash` 是**当前能动用的现金**。A 股是持续持仓的账户，两者能差一半
> （688152 那轮：账户 5 万、已持 21,574 元 ⇒ 可用现金只有 28,426 元，
> 不传 `--cash` 时引擎给出 974 股 = 35,765 元 = **买不了**）。
> 传了之后 `rec.qty` 受现金封顶、`meta.cash` / `rec.pct_cash` 落进 JSON、
> 渲染器在「口径问题」里自动加一条，并在股数旁标「引擎上限」。

**只有第 ② 步的 `notes.json` 需要模型写**（判断与叙述，≈1.5~2.5K token）。
`notes.json` 的所有字段都可选 —— 缺哪块就用数据兜底，不会出现空板块
（会显式写「未提供判断文字」）。完整示例见仓库根 `notes.example.json`。

Agent 仍需自己检索一手来源的部分（**不能省**）：
扫雷（解禁/减持/立案）、六维研究的公司业务与财务、估值水位对比、催化事件。

## 2. `battle_analyze.py` 做什么

| 顺序 | 内容 | 说明 |
|---|---|---|
| 1 | 取日线 | `bars_source.ash_bars()`（本地快照→进程内记忆→磁盘缓存→网络）。**不再走 `tdx_kline`** —— 那条通道单次返回 142KB 会超 token 上限、被迫落盘再读，链路又长又慢；新浪源实测 0.2~0.7s |
| 2 | 结构判定 | `rule123.evaluate(code, tmp_snapshot)` —— 与 CLI 完全同源 |
| 3 | 量价/预案单 | `probe_intraday.probe(...)`，**只取返回的 dict**（stdout 被重定向丢弃），不再解析文本 |
| 4 | 补算引擎不输出的量 | 均线族+方向、贴线真伪（±1/±2%/±3% 命中）、ATR、关键结构位（10/20/60/250）、上方枢轴阶梯、区间涨幅、60/120/250 分位 |
| 5 | **全档赔率枚举** | 入场候选 × 结构锚；剔除 `risk < 0.25×ATR`（纸面赔率）；R 到 t1 与"远端墙"两个目标 |
| 6 | 当日 5 分钟复盘 | 开高低收、收盘位置、**分钟涨跌量比（按相对前一根收盘判涨跌）**、分时段量能、尾盘 30 分钟占比 |
| 7 | 同行轻量对照 | 阶段涨幅/距年内高/距 MA20/ATR%，**全部由日线自算**——不读行情接口的「区间涨幅」字段（见 output-pitfalls 锐捷 301165 那条） |

产物 `analysis.json` 里两份赔率：
- `odds` —— **全矩阵**（70+ 组），进报告的折叠附录；
- `odds_primary` —— **主表**，止损统一取引擎结构锚（与原报告「止损统一取结构锚 EMA10 50.56」同口径），一个入场一行，8 行左右；
- `odds_recommend` —— 自动挑出的"可执行且赔率最高"档，四条过滤：可预挂 / 买价 > 结构止损位（不是开仓即止损）/ 买价 ≤ 买区上沿（不追高）/ 风险 ≥0.25×ATR 且需回落 ≤4%。

## 3. `notes.json` 字段表

| 键 | 用途 | 缺省行为 |
|---|---|---|
| `title` / `h1` / `code_label` / `meta_line` | 页头 | 由 meta 自动拼 |
| `thesis_html` / `thesis_plain` | 首屏结论（可含 `<b>`）；`_plain` 进一页汇总 | 标注「未提供」 |
| `badges` | 首屏徽标 `[{cls,txt}]`，cls ∈ b-t1/b-ok/b-warn/b-no | mode/recommend/regime 自动出 |
| `kpi_extra` | 首屏额外 KPI `[[名, 值]]`（成交/换手/市值/股本） | 不显示 |
| `best_title` / `best_note` | 最高 R 卡标题与说明 | 自动生成 |
| `mode_note` / `plan_note` | 模式卡、止损卡的注解 | 空 |
| `caliber_notes` | **口径问题**（硬止损噪声带/买区上抬/两档执行腿）—— 数组，每项一段 `<p>` | 按 `hard_noise`/`buy_lo_adjusted` 自动生成 |
| `odds_note` | 赔率表口径说明 | 空 |
| `intraday_note` / `vp_note` / `vp_verdict_note` | 量价三节注解 | 空 |
| `vp_verdict` | **强制**「当日判定 + 近 20 日判定」两行 `[{dim,verdict,basis}]` | 按分时与 20 日量价自动生成 |
| `fund_body` | 4.1 公司是什么（HTML） | 占位 |
| `fin_rows` / `valuation_rows` | 财务、估值表（3 列：项/值/备注） | 占位 |
| `valuation_note` / `catalysts` | 估值结论、催化清单 | 占位 |
| `minesweep` / `minesweep_note` | 扫雷（数组，每项一 `<li>`）| 占位并提示"必须检索一手来源" |
| `bigstruct_rows` / `bigstruct_note` / `bigstruct_oneline` | 大结构表（阶段/价格/日期/幅度）、注解、一页汇总用一行 | 空 |
| `veto` / `veto_note` | 三道总否决 `[{no,item,judge,verdict}]` | 空表 |
| `peers_note` | 龙头对照结论（主标的 vs 龙头，优先做谁） | 空（表格数据由脚本算） |
| `score_invest` / `score_trade` / `score_invest_li` / `score_trade_li` | 双轨打分（**禁止合成总分**） | `—` |
| `best_rows` | **接管「最高盈亏比路径」卡片的 KPI 行** `[[名, 值]]` | 用引擎按 `odds_recommend` 生成 |
| `exec_rows` | **接管执行方案的核心行**（动作/买入价/止损/数量/金额/单笔风险）`[[名, 值]]` 或 `[[名, 值, 备注]]` | 用引擎按 `odds_recommend` 生成的核心行 |
| `exec_rhythm` / `exec_invalid` | 加仓减仓节奏 / 失效条件 | 不显示 |
| `summary_rows` | 一页汇总（可整表覆盖） | 脚本自动生成 |
| `disc_constraints` / `disc_data` | 免责声明里两行 | 自动 |

`_` 开头的键（如 `_README`）会被忽略，可用来写注释。

## 4. 模板与插槽

- 模板：`templates/battle_report.html`，占位符形如 `{{KPI_ITEMS}}`，共 ~52 个。
- 渲染器：`report_render.py` —— 单次正则替换（**只扫模板，不重扫替换结果**，所以 notes 里写
  `{{...}}` 不会引发嵌套替换）。
- **改版式只改模板**；**改数据来源或算法只改 `battle_analyze.py`**；渲染器负责把数据摆进去。
- 新增插槽：模板里加 `{{NEW_SLOT}}`，`render()` 的 `slots` 字典里加一项即可。
  模板里出现未定义插槽 → 渲染结果写 `<!-- 未定义插槽 NEW_SLOT -->`，
  且 `tests/report/test_battle_report.py::test_template_slots_all_defined` 会直接失败。
- 渲染器每次都会跑 `check_html()`：div/table/tr/td/th/p/ul/li/span/b/code 的开关配对 +
  残留占位符扫描。历史上手写 43KB 时断过一次 CSS（`.best{R:}}`），这条自检就是为此。

## 5. 为什么不上前端框架 / 模板引擎

问过："用前端框架会简单很多吧？"

**渲染引擎不是瓶颈** —— 实测模板渲染 **0.014 ms**（7 行赔率表，1000 次均值）。
真正的时间在**模型逐字吐 token**（≈139 tok/s）。换 Handlebars/Jinja2/Vue
一秒也省不下来，因为要省的是"模型写的字节数"，而这跟用什么引擎无关。

具体到这里还有三条硬约束：
1. **运行环境**：skill 跑在裸 Python（3.11/3.13）里，没有 npm、没有构建步骤、
   网络不稳（本机装包常失败）。引入 Jinja2 就多一个依赖；Vue/React 还要 node + 构建产物。
2. **收益为零**：渲染器里"循环/条件"本来就是 Python 函数（`build_odds_rows` 等），
   比模板语法更灵活、更好调试；`{{KEY}}` 正则替换 30 行代码，没有学习成本。
3. **鲁棒性**：纯字符串替换的失败模式只有"插槽未定义"，一眼可见；
   模板引擎的失败模式（未定义变量静默变空、作用域继承、autoescape 策略）反而更难查。

⇒ **结论：该固化的是"版式"和"重复计算的数字"，不是换渲染器。**
真要上框架，唯一有意义的场景是"想在浏览器里交互式改数据再导出" —— 那是另一个需求。

## 6. 耗时对照（同一份数据）

| 环节 | 旧（手写 HTML） | 新（模板化） |
|---|---|---|
| 取数 + 结构 + 量价 | ≈134s（含 142KB tdx 通道往返） | 同（改走新浪源可再省） |
| 结构核验/赔率/同行/分时 | ≈161s（5 个临时脚本、5 轮往返） | **一条命令，1 轮** |
| 写报告 | **97.9s**（模型吐 12,783 tok） | **只写 notes.json（≈2K tok）** |
| 校验 | 26s | 渲染器内置自检，<1s |

模型侧输出量：**12,783 tok → ≈2,000 tok（−84%）**。

同一流程在 2026-09-21 的两次连续实测（脚本侧耗时，不含模型写 notes）：

| 票 | `battle_analyze.py` | `report_render.py` | 报告体积 |
|---|---|---|---|
| 688152 麒麟信安 | ≈13s | <1s | 55.9 KB |
| 300657 弘信电子 | **13s**（23:57:07→23:57:20） | <1s | 49.9 KB |

即「取数 → 结构 → 量价 → 全档赔率 → 同行 → 分时 → 出报告」整条链路的
**机器时间 ≈14s**，人类可感知的剩余耗时全部来自模型写 `notes.json`（判断叙述）。

## 7. 已知坑

1. **`_dir_of` 用的是"末值与 5 根前比"** —— 均线方向判一条均线是否上行，窗口太短会在
   横盘里抖动。贴线真伪判据（output-pitfalls #21）要求"±1% ≥2/8 且方向不为负"，
   方向给 0（走平）时按"不为负"放行。
2. **`pivots(w=3)` 永远看不到最近 3 根内的高点**（右侧没有 3 根确认）——
   而它常常正是最贴买价的那道压力（东材 9-17 的 55.50 就是这样漏掉的）。
   `battle_analyze` 因此显式把「近 10 根高点」补进阶梯。
3. **主表必须只用统一的结构止损锚**。全矩阵 70+ 行直接铺进报告没法读；
   但**全档枚举这件事不能省** —— 它进折叠附录（`<details>`）。
4. **`notes` 里的 `warn` 文本必须转义**：`薄止损（<0.35×ATR）` 里的 `<` 会被浏览器
   当标签开始，吞掉后半句。渲染器对 warn 走 `esc()`，有专门测试钉死。
5. **引擎判不出买区（wait / 枢轴不足 / ERR）不是崩溃**：`analyze()` 会照常出
   `analysis.json`，但在 `meta.plan_warning` 留痕，渲染器把它顶到「口径问题」第一条。
   纯单调的合成价格序列一个枢轴都没有 —— 写测试造数据时必须带摆动。
6. **`--cash` 与 `--account` 是两个口径，都要传**（2026-09-21 跑 688152 暴露）。
   `--account` 只用于风险预算（账户 × 1.5%），`--cash` 才是金额封顶。
   持续持仓的账户上两者能差一半，只传 `--account` 会算出「买不起的股数」。
   引擎侧对应 `ash_lots(..., cap_amt=cash)` —— 旧版 `ash_single_cap` 把
   「账户×30%」闸门去掉后只剩 5 万绝对额，对 5 万账户就是 100%，薄止损会把
   股数放大到极致（974 股 = 71.5% 账户）。
7. **注释说「由渲染器判定」的字段，要在渲染器里真的找得到那段逻辑**（2026-09-21）。
   `struct.tie_line_verdict` 长期恒为 `None`、注释写着「由渲染器按 ±1% ≥2/8 与方向判定」，
   而 `report_render.py` 里 grep `tie_line` 是 **0 匹配** ⇒「均线下行 ⇒ 贴线存疑」
   这条最重要的警告被静默掉了一整轮。现已固化成 `battle_analyze.tie_line_check()`：
   真贴线 = 近 8 根 ±1% 命中 ≥2 **且** 均线方向不为负；否则判「存疑」并说明是
   「方向为负（价格反超一条下移的线）」还是「±1% 命中不足（只是在均线附近运行）」。
   渲染器现在把 `tie_line_verdict.ok == False` 无条件顶进「口径问题」第 1 条。
   **同类隐患的检查办法**：对每个「由渲染器判定」的注释，去渲染器里 grep 一次字段名。
8. **`notes.exec_rows` 必须是「覆盖」而不是「追加」**（2026-09-21 跑 300657 暴露）。
   `build_exec` 原本在引擎生成的 7 行核心行后面 `append` notes 的行 —— 结果执行方案
   表里同时出现**两套互相打架的口径**（引擎：买 38.49 / 止损 38.00 / 700 股；
   人工：买 37.65 / 止损 36.67 / 600 股），阅读者无从判断该执行哪一套。
   现已改为：`exec_rows` 存在时**整体替换核心行**，但**保留与档位无关的事实行**
   （目标1 / 目标2 与远端墙 / 挂单有效期 / 预挂可行性）—— 人工接管判断，不该连数据
   一起删掉。3 个用例钉死（覆盖生效、事实行保留、不传时行为不变）。
   **通用规律**：凡是「脚本给默认值 + notes 可覆盖」的插槽，都要明确是 replace 还是 append；
   渲染器里两类语义混用，是这类报告最隐蔽的错误来源。
   ★ **2026-09-22**：`exec_rows` 从 `kv_rows()`（只吃 2 元组）改为 `rows()` —— 表头本来就是
   「项 / 值 / 备注」三列，notes 需要能给「两方向预案」这类行补第三列说明。写 3 元组
   `[[名, 值, 备注]]` 现在合法；写 2 元组也照常工作（第三格为空）。
9. **凡是「由引擎数据算出来的 KPI 行」都要留 notes 覆盖口**（2026-09-21 跑 300657 暴露，
   与第 8 条同源）。首屏「最高 R 卡」的标题能覆盖（`best_title`）、KPI 行不能覆盖 ⇒
   标题写人工选的档（买 37.65 / 止损 36.67 / 600 股），KPI 却是引擎推的薄止损档
   （买 38.49 / 止损 38.00 / 700 股）—— **同一张卡片里两个买价**，比不显示更危险。
   新增 `best_rows`（与 `exec_rows` 同语义：整体替换）。检查办法：对每个
   `notes.*` 覆盖字段，倒过来问「这个卡片还有哪些行是引擎算的、我没法改？」
10. **同一屏里的对照行必须与正文用同一张表**。`build_best` 的「最差档」原本取
   全矩阵 `odds`（300657 是 78 组）的末位 ⇒ 显示 R 0.26，而报告正文主表用
   `odds_primary` ⇒ 同一价位的 R 是 1.00。两个数字都"对"，但读者只会认为报告算错了。
   已改为取 `odds_primary`。「名义最高 R」保留全矩阵口径是**有意的**（那张卡片的
   用途就是提示"存在更高 R 但不可执行"），但要在文案里写明它不可执行。
11. **趋势单（T0）没有固定目标 ⇒ 目标行必须「如实说明」，不能打印空值**（2026-09-22 跑
   东微半导 688261 暴露）。第 9 节的事实行原本无条件打印
   `目标1 —（到达减 1/3~1/2，止损上移到成本或均线）` 与 `— / 114.30`：T0
   （`ma_reclaim_break`）分支下引擎**不给目标**（`plan["targets"]` 恒为 `None`，
   顶层 `targets.t1` / `t2_engine` 也是 `None`），于是一个空格子配一句「到达减 1/3」
   的操作指令，自相矛盾；而「什么价卖」是作战计划的硬要求。
   ★ **修法不是硬塞一个目标价** —— 用户 2026-09-06 已明确纠正「拿前高/量度当目标位 =
   框架错配」，T0 的纪律是「不设固定目标、用移动止损让利润奔跑」。现在改为：说明
   「本模式按移动止损（MA5 / 大阳中点）管理，不设固定目标位」，并**回退到顶层 targets
   的 `wall_far` / `ath`** 作「参考阻力」列出（文案明确标注「不作为目标位」）。
   新增共用辅助 `target_display(a)`，`build_plan_rows` 与 `build_exec_rows` **两处共用**
   （此前两处各写一遍取值逻辑，且只有一处会读顶层）。
